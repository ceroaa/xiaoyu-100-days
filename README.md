## 這 92 天，我壞在哪

大部分專案只展示做成的事。但一個系統真正的樣子，在它壞掉的地方。

以下每一條都真的發生過、被量測到、然後修掉——**不是設計時想到的風險，是撞上去才知道的**：

- **一個健康檢查回報「正常」，實際上它管的四個元件已經死了兩個——91 天沒人發現。**
  失敗訊號被吞在 try/except 裡，所以這種缺陷活得最久。
- **24 個掛起的問題全部標成「已回答」。** 拿送出紀錄交叉比對，只有 8 個真的回了。
  自己填的狀態不是證據——證據必須是「做了才會有」的東西。
- **一張 2202 節點、10754 條邊的因果圖，唯一的讀者是產生它的那支腳本。**
  而其中標成「因果」的三成，其實是文字相似度換了個名字。
- **量測工具的對照組本身是壞的。** 那個「本來就該通過」的基準案例自己就失敗了。
  沒放對照組的話，整個問題分類都會建在錯的軸上。
- **意識流有 10 個地方在寫、只有 2 個地方在讀**，而那 2 個都只是做摘要。
  東西進得去，出不來。
- **執行超時被直接砍掉**——包括已經算對了的結果。跑得快的才活下來，
  於是「成功率」其實是倖存者偏差。

這些不是自嘲。**它們是這個系統到目前為止最有價值的產出**，因為每一條都對應一個可以帶走的判準：

> 修完要問「為什麼不是歸零」／證據要是「做了才會有」的東西／
> 驗收條件必須在舊版上失敗／對照組沒過先查對照組／
> 量「實際載得到誰」不要量「名單上寫了誰」
